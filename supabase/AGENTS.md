## Purpose

The backend artifacts for Curio's online layer: the database schema and its Row Level Security policies. The Android client that consumes them lives in `app/src/main/java/com/curio/app/data/supabase/`.

## Ownership

- `schema.sql` — the whole online schema in one idempotent script: `profiles`, `cloud_captures`, `community_cards`, `community_reactions`, `community_comments`, `community_comment_reactions`, `community_reports`, `community_admins`, `moderation_actions`, `friend_requests`, `dm_messages`, their RLS policies, indexes, the immutability triggers, `curio_are_friends()`, the moderation functions (`curio_file_report`, `curio_handle_report`, `curio_moderate_remove_card` / `_remove_comment` / `_hide_member`, `curio_set_community_admin`, `curio_remove_community_admin`, `curio_admin_can`, `curio_member_hidden`), the expiry sweep function and a self-check block.

There is no deployment automation: the file is pasted into the Supabase dashboard's SQL Editor (Database → SQL Editor → Run). Re-running it is safe by design.

## Local Contracts

- **DM encryption envelopes:** `dm_device_keys` holds only public device keys; `dm_key_envelopes` holds per-device RSA-OAEP-wrapped conversation keys. Envelope SELECT is recipient-only, and its trigger requires the canonical conversation ID plus a registered non-retired recipient device. The Android client provides the cryptographic recipient-key correspondence; the database never receives private or plaintext AES keys. A sender also wraps the SAME conversation key for its OWN devices (`recipient = auth.uid()`), which the message trigger requires, so the validator accepts that case by recovering the peer from the id itself (`curio_dm_conversation_peer`, which also rejects a non-canonical ordering) and re-checking that peer as an accepted friend. `curio_dm_conversation_of()` is the ONE canonical-id definition, shared with both `dm_messages` triggers — never re-derive that string inline.
- **DM mode and deletion:** `dm_conversations.encryption_enabled` is the server-authoritative, two-participant mode for new DMs. Its RLS and party-pinning trigger prevent a client from changing the chat members; `dm_messages` has an insert trigger that rejects plaintext while encryption is on and ciphertext while it is off. Existing conversations without a row default to encrypted. A `dm_messages` DELETE is sender-only unsend.
- **Deleting a conversation (§5h) has exactly two shapes, and they are not interchangeable.** "Delete for me" is the per-user marker `dm_conversation_hidden` (owner-only RLS), plus the device's own cached copy — the other participant keeps every message, and the thread REAPPEARS by itself once they write again, because `threads()` only hides a conversation whose newest message is older than the marker's `hidden_at`. "Delete for both of us" is the `security definer` function `curio_delete_dm_conversation(other uuid)`: it removes the pair's `dm_messages`, BOTH participants' `dm_conversation_hidden` rows and the `dm_conversations` row, re-checking only that the caller is one of the two parties and that a conversation actually exists. It is deliberately NOT gated on the friendship still existing (unfriending is exactly when someone clears a thread) and is granted to `authenticated` with everything else revoked. Removing another person's messages is not expressible as a table grant, which is why it is a function and not a DELETE policy.
- **Realtime publication (§5g) is what makes the social surfaces live.** Operator guide (publication, replica identity, RLS/JWT rules, private-channel options, troubleshooting): `docs/REALTIME_SETUP.md`. `dm_messages`, `dm_reactions`, `dm_typing`, `friend_requests`, `community_cards` and `community_comments` must be members of `supabase_realtime`, and the app subscribes with the user's access token, so RLS still decides what a device hears. `replica identity full` is set on the tables whose FILTERED updates/deletes are matched against the old row (`dm_messages`, `friend_requests`, `dm_reactions`) — losing it silently drops those events and the app drops to polling without any error.
- **RLS is the security boundary.** The Android app ships only the public URL + publishable/anon key, so every table must keep RLS enabled with policies for `authenticated` only. Never add an `anon` policy, never disable RLS, and never grant the app a service-role key.
- **Text only.** The tables carry no media columns. Capture sync mirrors text metadata and serialized text content; images, audio and screenshots never sync, and community cards are rebuilt on each device with the app's own share-card renderer.
- **24-hour cards.** `community_cards.expires_at` defaults to `now() + interval '24 hours'` and the insert policy refuses anything longer than 25 hours. Every read filters `expires_at > now()`, so expiry holds even before the sweep runs; `curio_purge_expired_cards()` is housekeeping (optionally scheduled with `pg_cron`). Replies (`community_comments`) cascade off the card, so a comment can never outlive its 24-hour card. `community_comment_reactions` (§4c) is the same 24-hour leash one level down: it cascades off its reply, and its SELECT policy re-derives the reply's card to check `expires_at > now()` plus both sides' Online Mode, so a heart can never be counted on a card that has expired. **A reply heart needs its OWN table** — `community_reactions` is keyed by `(card_id, user_id)`, i.e. one row per member per CARD, so it cannot carry a per-reply heart; `community_comment_reactions` is keyed by `(comment_id, user_id)`. Replies also BRANCH (`parent_id`, any depth), which the client renders with `branchRenderList()`.
- **Captions and replies are text.** A card carries the card's own `fact_text` plus the poster's optional `caption` (≤180 chars), and each reply is ≤400 chars — both enforced by check constraints, both with no media column anywhere in sight.
- **Evolution stays idempotent.** `create table if not exists` never touches an existing table, so columns added later (e.g. `caption`) also appear as `alter table … add column if not exists` plus a guarded constraint block, and the table list in the self-check is updated in the same edit.
- **Identity comes from the token, not the client.** `owner` / `user_id` / `reporter` default to `auth.uid()`, so the app never sends an identity column and cannot attempt to post or react as somebody else.
- **Online Mode gates community access** on both sides: the policies require the acting user's and the card author's `profiles.online_mode_enabled` to be true, and the client mirrors the switch through `SupabaseClient.updateOnlineMode` (an upsert, so a brand-new account gets its row).
- Cards are immutable once posted (there is deliberately no update policy), and only the author may delete one early.
- **Social layer (§5b–5d).** `profiles.discoverable` (default true) plus a second SELECT policy exposes the PUBLIC identity — id, display name — but only for accounts with Online Mode on, so turning the switch off hides you from search. `friend_requests` carries its own status, so an `accepted` row IS the friendship; a generated `pair_key` keeps one request per pair in either direction and its partial unique index (`where status <> 'declined'`) still allows a fresh ask after a decline. `dm_messages` is text only, readable by its two participants, and insertable ONLY between accepted friends (via `curio_are_friends`, a `security definer` boolean test, granted to `authenticated`).
- **Immutability triggers.** The two sides of a request or a message are pinned by `curio_pin_request_parties()` / `curio_pin_message_parties()`. RLS cannot express this: an UPDATE policy's `USING` sees the old row and its `WITH CHECK` sees the new one, so neither can compare them — without the triggers an addressee could accept a request and swap the requester for a third party in the same statement.
- **Discoverability is the consent boundary.** Reads/writes of the social tables require Online Mode on for the acting user, and asking/messaging additionally requires it on for the other side (+ `discoverable` when asking).
- **Moderation (§5a + §6b) is database-managed privilege, never a client claim.** `community_admins` carries `role` (`owner` | `admin`) and five independent switches (`can_delete_posts`, `can_delete_replies`, `can_handle_reports`, `can_manage_admins`, `can_ban_members`); the single permission test is `curio_admin_can('posts'|'replies'|'reports'|'admins'|'bans')`, which every policy and function calls (the owner is always true, anything unrecognised is a NO). `@jugnu`'s profile is seeded as the OWNER by `schema.sql`, and the owner is protected in SQL — `curio_set_community_admin` refuses to touch or create one and `curio_remove_community_admin` refuses to remove one — so the community can never lock itself out of its own controls. **Reports name exactly one of `card_id` / `comment_id` / `target_user`** (`community_reports_one_target`), one partial unique index per kind keeps ONE row per reporter per target, and `curio_file_report` REFRESHES that row on a repeat report (the old `(card_id, reporter)` unique constraint is dropped — a second report used to answer with an error). `curio_handle_report` works one queue row (`dismiss` | `remove_content` | `hide_author` | `reopen`) with a per-ACTION permission test, and every decision writes a `moderation_actions` row (actor, target, reason, note) whose SELECT is `reports`-permission only. **A ban is content-only:** `profiles.banned` / `banned_at` / `banned_by` / `ban_reason`, enforced by RESTRICTIVE select + insert policies through `curio_member_hidden(subject)` (a `security definer` test, so the profile is read where policies would hide it) — the author's cards and replies disappear and they cannot post, while their account keeps working and a `reports`-holder can still review the content. A removal or a hide REQUIRES a reason (`raise exception 'curio: a reason is required'`). All moderation functions are `security definer`, `revoke all … from public, anon`, `grant execute … to authenticated` — never a table grant.

## Work Guidance

- Keep `schema.sql` idempotent: `create … if not exists` plus `drop policy if exists` before each `create policy`, so the file can be re-pasted after an edit.
- Add a table only together with its RLS policies, indexes and grants in the same edit, plus a line in the self-check block at the end.
- Keep the self-check block honest: it prints PASS/FAIL notices for RLS coverage, anon exposure and missing tables after a paste.

## Verification

- Run the file in the SQL Editor and read the `NOTICE`/`WARNING` lines the self-check block raises (every table exists, RLS on, no anon policies).
- Verify from the app: signed out → the feed is locked; Online Mode off → the feed is locked even when signed in (RLS refuses too, by design).
- There is no local Postgres in this workspace, so schema changes are validated by reading the policies and by the dashboard run — never by a local migration tool.
